## 3. D 값을 어떻게 바꿨는지

| 단계 | 판정식 | 기준 | 문제 |
|---|---|---|---|
| 처음 | 논문① `D = −14.773 + 0.406a + 0.662b` | 0.463 | 연예인 데이터에서 57% 만 맞음 |
| 팀원 | 같은 식 이름, 실제 계산은 `b − C` | −5.5 / −6.0 | 이름과 식이 달라 혼선 |
| 지금 | **색상각 `h = atan2(b, a)` (도)** | **47°** | 홍조(a 큼)에 강함 |

- `b − C` 와 `h` 는 사실상 같은 걸 본다(둘 다 a 대비 b 의 비율). `h` 가 각도라서 해석이 쉽고
  팀 합의안이라 `h` 로 통일했습니다.
- 퍼센티지: `웜 확률 = 1 / (1 + e^-((h − 47) / 6))`
- 판정: `h > 49° 웜` / `45~49° 경계형` / `h < 45° 쿨`

### 기준선이 54° 가 아니라 47° 인 이유
팀 안의 54° 는 **흰 종이 좌표를 손으로 찍어** 측정한 값입니다.
우리 파이프라인은 종이를 자동으로 찾아 포화·그림자 화소를 빼고 평균을 내므로
같은 사진에서도 h 값이 다르게 나옵니다. 라벨이 확실한 웹캠 사진으로 재측정한 값:

| 사진 | 라벨 | 측정 h | 54° 기준 | 47° 기준 |
|---|---|---|---|---|
| 523_05 | 웜 | 51.2° | ✗ 쿨 | ✓ 웜 |
| 328_04 | 웜 | 50.0° | ✗ 쿨 | ✓ 웜 |
| 328_03 | 쿨 | 43.1° | ✓ 쿨 | ✓ 쿨 |
| 190617660 | 쿨 | 33.0° | ✓ 쿨 | ✓ 쿨 |

54° → 4장 중 2장, 47° → 4장 중 4장. 중간값이 46.9° 여서 47° 로 두었습니다.
경계폭도 ±4° → **±2°** 로 좁혔습니다(팀 안의 ±4° 는 웜·쿨 간격이 22° 일 때 값인데
우리 측정은 간격이 7.5° 라 ±4° 면 전부 경계형이 됩니다).

**중요: 기준선 47° 는 라벨 4장으로 잡은 잠정값입니다.** 이번 주 표본이 모이면
`tools/fit_threshold.py` 로 다시 뽑습니다. 촬영 기기가 바뀌면 기준선도 이동합니다.

모든 숫자는 `data/reference/season_reference.json` 한 곳에만 있습니다. 코드는 안 고칩니다.

## 4. 백엔드 ↔ 웹 연결 방법

UI 는 이미 `templates/index.html` + `static/main.js` + `static/style.css` 로 push 되어 있고,
`main.js` 가 `POST /api/diagnose` 로 사진과 가이드 박스 좌표를 보내고 있습니다.
**즉 연결 자체는 이미 돼 있고, 서로 어긋난 부분 4곳만 맞췄습니다.**

### 실행 방법 (이게 전부입니다)
```
cd C:\Users\user\Desktop\시보프\personal_color
python app.py
```
→ 브라우저에서 `http://127.0.0.1:5000` 열기 → 카메라 권한 허용 → 촬영.
`app.py` 하나가 화면(`/`)과 진단 API(`/api/diagnose`) 를 같이 띄우므로 서버는 하나만 켜면 됩니다.

### 맞춘 부분 4곳
| # | 문제 | 고친 곳 |
|---|---|---|
| 1 | 프론트는 `{x, y, width, height}` 로 보내는데 백엔드는 `{x1,y1,x2,y2}` 만 받았다 (가이드 박스가 무시됨) | `backend/vision/paper.py` — 두 형식 다 받도록 |
| 2 | 재촬영 안내(400)를 "서버 응답 오류" 로 뭉개서 왜 실패했는지 안 보였다 | `static/main.js` — `data.error` 문장을 그대로 표시 |
| 3 | 웜/쿨 판정이 화면에 아예 없었다 (4계절 퍼센티지만 있었음) | `templates/index.html` + `main.js` — `tone` 한 줄 추가 |
| 4 | '보정 후' 사진이 CSS 필터로 만든 가짜였다 | `app.py` 가 실제 보정 사진을 base64 로 보내고 `main.js` 가 그걸 표시 |

4번이 중요합니다. 우리 프로젝트 제목이 "**근거를 보여주는**" 이라서, 보정 전/후 비교가
가짜 필터면 근거가 아니라 연출이 됩니다.

### API 규격 (프론트에게 줄 문서)
```
POST /api/diagnose   (multipart/form-data)
  image  : 사진 파일 (필수)
  coords : {"x":0.62,"y":0.55,"width":0.2,"height":0.25}   (선택, 0~1 비율. 없으면 자동 탐지)
```

성공 200
```json
{ "ok": true,
  "tone": { "verdict": "warm", "label": "웜", "warm": 63.1, "cool": 36.9 },
  "percentages": [ { "key": "autumn", "name": "가을 웜", "value": 45.8, "color": "#C98A5B" }, ... ],
  "best_group": "가을 웜",
  "reliability": 90,
  "reliability_msg": "조명·각도 모두 양호합니다.",
  "message": "가을 웜 톤에 가깝습니다.",
  "corrected_image": "data:image/jpeg;base64,...",
  "warnings": [] }
```

재촬영 400
```json
{ "ok": false, "code": "retake_required",
  "error": "흰 종이가 하얗게 날아가 기준색으로 쓸 수 없습니다. 종이에 조명이 직접 닿지 않게...",
  "reasons": ["...", "..."],
  "corrected_image": "data:image/jpeg;base64,..." }
```

`code` 종류: `retake_required`, `paper_not_found`, `face_not_found`, `white_balance_failed`,
`no_image`, `bad_image`. 프론트는 `error` 문장을 그대로 띄우고 "다시 찍기" 버튼만 주면 됩니다.

### 확인 체크리스트
1. `python app.py` 가 에러 없이 뜨는지
2. 촬영하면 결과 화면에 **웜/쿨 한 줄 + 4계절 막대 + 신뢰도** 가 다 나오는지
3. 조건 나쁜 사진으로 찍었을 때 "다시 촬영해주세요 + 이유" 가 뜨는지
4. '보정 후' 사진이 원본과 실제로 색이 다른지 (같으면 보정이 안 된 것)

## 5. 지금 데이터 상태 (솔직한 신호)

웹캠 9장 중 **7장이 `retake_required`** 입니다.
- 흰 종이가 하얗게 날아감 (3장, 깨끗한 화소 13~57%)
- 얼굴 좌우 색 차이 ΔE 8.4~16.3 (4장, 한쪽에서만 조명)

품질 게이트가 제대로 작동하고 있다는 뜻입니다. 이번 주 재촬영은 반드시 아래 조건으로:

1. 흰 A4 를 얼굴 옆 같은 평면에 두기 (조명 직접 받지 않게)
2. 정면 조명, 창·스탠드 한쪽에서 받지 않기
3. 화장 안 한 상태, 얼굴이 화면 가로의 15% 이상
4. 같은 노트북·같은 장소·같은 시간대

같은 사람을 조건 맞춰 2장씩, 웜/쿨 각 5명 이상이면 기준선을 제대로 확정할 수 있습니다.
